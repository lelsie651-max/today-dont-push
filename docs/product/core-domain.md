# 核心领域模型

本文档解释《今天别硬撑》第一版纯领域模型的术语、数值范围与设计动机。
实现位于 `packages/domain`，全部为只读、可序列化的普通对象 + 返回 `DomainResult` 的工厂函数；
领域层不依赖任何第三方库，不读取当前时间，不生成随机 ID，不接触数据库。

## 术语表

| 术语 | 类型 | 含义 |
| --- | --- | --- |
| 每日签到 | `DailyCheckIn` | 用户对"今天状态如何"的一次回答：能量档位 + 负担标签 + 可选备注 |
| 能量档位 | `EnergyLevel` | 今天可用的心理/生理能量总量，粗粒度三档 |
| 负担标签 | `StrainTag` | 解释"今天为什么累"的可多选标签 |
| 时间窗口 | `TimeWindow` | 毫秒时间戳区间 `[startAtMs, endAtMs)`，由外部传入 |
| 可用时间 | `availability` | 今天真正"属于自己、可自由支配"的时间段集合 |
| 固定承诺 | `FixedCommitment` | 必须在特定时间段发生、不可挪动的事（会议、通勤、预约） |
| 弹性任务 | `FlexibleTask` | 今天尽量做、但开始时间与形态可以协商的事 |
| 最低可行版本 | `MinimumViableVersion` | 任务的降级形态：状态很差时用最小代价拿到核心价值 |
| 每日规划输入 | `DailyPlanningInput` | 一天的完整画像：签到 + 可用时间 + 固定承诺 + 弹性任务 |

## 数值范围与不变量

### 能量档位（EnergyLevel）

严格限定为 `20 / 50 / 80` 三档。刻意的粗粒度：人在疲惫时不应被迫做精细自评，
三档足以让调度做出"今天硬撑还是降级"的决策。

### 负担标签（StrainTag）

`poor_sleep`（睡眠差）、`physical_discomfort`（身体不适）、`low_mood`（情绪低落）、
`exhausting_commute`（通勤耗竭）、`meeting_heavy`（会议过多）、`urgent_deadline`（截止逼近）、
`interpersonal_stress`（人际压力）、`other`（其他）。

- 不得重复；
- 选择 `other` 时 `note` 必填（保证"其他"是可解释的）；
- `note` 去除首尾空格，最长 200 字符。

### 时间窗口（TimeWindow）

- `startAtMs` / `endAtMs` 必须为有限的安全整数；
- `endAtMs` 必须严格大于 `startAtMs`；
- 领域层不处理时区、不读取当前时间：时间戳全部由外部提供，跨午夜只是"更长的区间"，天然合法。

### 固定承诺（FixedCommitment）

- `title` 去空格后非空，最长 100 字符；
- `energyDemand` 为 1–5 整数（1 轻松 → 5 透支）。

### 弹性任务（FlexibleTask）

- `priority`：`must`（今天必须完成）/ `important`（重要）/ `optional`（可做可不做）；
- `estimatedMinutes`：5–480 分钟整数（小于 5 分钟的不值得规划，超过 8 小时的应拆分）；
- `energyDemand`：1–5 整数；
- `emotionalResistance`：0–3 整数（0 无阻力 → 3 强烈抗拒）。它独立于能量消耗：
  一件事可以"不累但非常不想做"；
- `deadlineAtMs` 可选，若提供必须为有限的安全整数；
- `minimumVersion` 可选，但其耗时与能量**不得高于**原任务——降级版本的意义就是更轻。

### 每日规划输入（DailyPlanningInput）

- `localDate` 为真实存在的 `YYYY-MM-DD`；`timeZone` 非空（原样保存，领域层不解释）；
- `availability` 至少一个窗口；返回结果按开始时间排序、互不重叠（边界相接不算重叠）；
- `commitments` 互不重叠，且每项必须**完全位于**某个 availability 内
  （承诺不能占用"不属于自己"的时间）；
- `commitments` 与 `tasks` 的 id 在同一天内必须唯一（跨类型也不允许重复）；
- `tasks` 允许为空——"今天什么都不想做"是合法输入，正是本产品要善待的状态。

## 为什么区分固定承诺与弹性任务

这是本产品最核心的建模决策：

1. **时间属性不同**。固定承诺"钉"在具体时间上，只能被尊重；弹性任务只声明
   总耗时，可以放进任何空闲段。混为一谈会让调度器误以为会议也能挪走。
2. **协商空间不同**。状态差时，弹性任务可以换时间、换形态（用最低可行版本替代）、
   甚至放弃（optional）；固定承诺没有这些选项，只能提前为其预留能量。
3. **负罪感来源不同**。"没做完任务"常有负罪感，"缺席承诺"则往往有外部后果。
   产品必须对两者说不同的话：对任务说"可以降级、可以明天再来"，
   对承诺说"我们把它算进了今天的能量账本"。
4. **对调度的作用不同**。固定承诺是"硬约束"（先扣掉），弹性任务是"待排物料"
   （在剩余能量与时间里协商）。未来的调度算法只消费 `DailyPlanningInput`，
   这个区分让它能分别处理两类东西。

## 错误处理约定

所有工厂函数返回 `DomainResult<T>`：

- 成功：`{ ok: true, value }`；
- 失败：`{ ok: false, errors }`，每条 error 含 `code`（机器可读）、`path`（字段定位，如
  `tasks[1].minimumVersion.energyDemand`）、`message`（人类可读）。

预期的输入错误一律通过返回值表达，不抛异常；调用方可以一次拿到全部问题，
便于 UI 一次性展示。
